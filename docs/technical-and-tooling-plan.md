# 游戏构建技术与工具选型

## 1. 文档定位

本文档只讨论项目建设方式：
- 用什么技术做
- 用什么工具做设计和开发
- 素材从哪里来
- 如何组织项目制作流程

本文档不展开具体玩法数值。

## 2. 项目建设目标

当前目标不是做一个“未来 PC 版的完整技术底座”，而是先高效做出一个适合微信小游戏的可玩版本。

所以技术选型原则应该是：
- 快速出原型
- 便于改数值
- 便于调整 UI
- 适合 2D 经营类游戏
- 未来可以继续扩展，但不为未来过度设计

## 3. 客户端技术选型

### 3.1 推荐方案
推荐优先方案：
- `Cocos Creator + TypeScript`

原因：
- 适合 2D 地图、卡片界面、节点操作和动画反馈
- 微信小游戏导出成熟
- 编辑器友好，方便快速搭界面
- 后续想增加动态表现比纯原生更省事

### 3.2 备选方案
可选但不优先：
- 微信小游戏原生 + TypeScript

适合场景：
- 团队前端能力很强
- 更在意包体和完全自定义工程
- 游戏表现更偏数据面板，而不是明显游戏化界面

当前不推荐优先走原生的原因：
- UI 和场景搭建效率不如 Cocos
- 后期加动效和页面切换成本更高

## 4. 编程语言与工程原则

### 4.1 编程语言
- `TypeScript`

原因：
- 数值系统适合类型约束
- 配置表和模块边界更清晰
- 更适合后续多人协作

### 4.2 工程原则
- 配置驱动优先
- 数值逻辑与界面逻辑分离
- 小游戏版先单机化
- 弱后端依赖

## 5. 项目模块建议

建议工程按以下方向拆分：

- `core/`
  - 规则计算
  - 月度结算
  - 评级逻辑

- `config/`
  - 区域配置
  - 能源配置
  - 科技配置
  - 贷款配置

- `modules/map/`
  - 地图节点
  - 区域进入与状态展示

- `modules/build/`
  - 建设方案选择
  - 成本计算

- `modules/company/`
  - 公司等级
  - 社会价值
  - 贷款与并购

- `modules/tech/`
  - 科技树

- `modules/ui/`
  - 公共弹窗
  - 面板
  - 卡片组件

- `save/`
  - 本地存档

## 6. 数据配置方案

### 6.1 建议采用配置表驱动
建议所有核心内容都从配置表读取，而不是写死在代码里。

必须配置化的内容：
- 区域类型
- 地区参数
- 能源类型
- 科技树节点
- 贷款档位
- 公司等级阈值
- 竞争公司触发条件

### 6.2 配置格式建议
开发阶段建议：
- 表格维护：`Excel`
- 导出使用：`JSON`

原因：
- 玩法和数值讨论时，表格最直观
- 程序读取时，JSON 最轻便

这也是最适合你当前阶段的方式。

## 7. 设计与原型工具

### 7.1 文档工具
推荐：
- `Markdown` 维护正式文档
- `Excel` 维护数值表

原因：
- Markdown 适合版本管理
- Excel 适合讨论数值和公式

### 7.2 原型设计工具
推荐：
- `Figma`

用途：
- 画界面草图
- 做流程页
- 做按钮、卡片、地图节点样式探索

为什么推荐：
- 轻量
- 协作方便
- 很适合小游戏 UI 设计

### 7.3 流程图工具
推荐任选一个：
- `Figma`
- `draw.io`
- `ProcessOn`

用途：
- 画核心循环
- 画页面跳转
- 画公司成长和科技解锁关系

## 8. 美术与素材方案

### 8.1 美术方向建议
小游戏版美术应追求：
- 清晰
- 易读
- 有轻科技感
- 成本可控

建议视觉形式：
- 地图偏扁平化
- 节点与建筑偏图标化
- 核心靠 UI 和数字反馈塑造经营感

### 8.2 首版需要的素材类型
- 地图底图
- 区域节点图标
- 能源设施图标
- 科技树图标
- UI 图标和按钮
- 简单事件插图
- 结算页装饰元素

### 8.3 素材获取方式建议
建议采用“采购 + 自制 + AI 辅助”三种组合。

#### 采购适合的内容
- UI 基础图标
- 通用按钮
- 通用小图标库
- 基础音效

可参考：
- [Kenney](https://kenney.nl/assets)
- [itch.io Assets](https://itch.io/game-assets)
- [CraftPix](https://craftpix.net/)
- [OpenGameArt](https://opengameart.org/)
- [Iconfont](https://www.iconfont.cn/)

注意：
- 商用前必须逐个核对授权
- 不要默认“能下载就能商用”

#### 自制适合的内容
- 地图
- 地区节点样式
- 科技树结构图
- 游戏主视觉风格

这些内容最影响项目辨识度，建议自己掌控。

#### AI 适合辅助的内容
- 概念图
- 宣传图
- 事件插图初稿
- 图标方向探索

AI 不建议直接生成最终整套 UI，因为一致性和可迭代性通常不够好。

## 9. 音频方案

小游戏首版音频应轻量。

建议优先准备：
- 主界面 BGM
- 建设完成音效
- 升级音效
- 警报音效
- 结算音效

可参考来源：
- [Pixabay Music](https://pixabay.com/music/)
- [Freesound](https://freesound.org/)
- [ZapSplat](https://www.zapsplat.com/)

同样需要核对授权。

## 10. 后端与数据存储

### 10.1 首版建议
首版建议采用：
- 本地单机存档为主
- 后端能力按需补

### 10.2 为什么不建议一开始重后端
- 你的核心风险不在服务端，而在玩法是否成立
- 先验证好不好玩，比先搭完整后台更重要

### 10.3 什么时候需要后端
当你需要以下能力时再接入：
- 云存档
- 排行榜
- 活动配置
- 用户登录同步

如果要接，建议优先考虑：
- 微信云开发

## 11. 开发流程建议

### 11.1 推荐顺序
建议按下面顺序推进：

1. 先定核心玩法文档
2. 再做 Excel 数值草案
3. 再做 Figma 低保真原型
4. 再搭 Cocos 工程骨架
5. 先做可玩原型
6. 最后补美术和表现

### 11.2 原型阶段目标
原型阶段只验证三件事：
- 选地区是否有策略乐趣
- 供能方案选择是否有明显差异
- 金钱与社会价值的取舍是否成立

如果这三件事成立，项目就值得继续投入。

## 12. 团队分工建议

如果是小团队，建议最低按这几个角色理解工作：
- 游戏策划：玩法、数值、系统设计
- 客户端开发：界面、逻辑、存档
- UI/美术：地图、图标、界面样式
- 可选技术美术/外包支持：补素材和动效

如果是你主导的个人项目，也可以按这个顺序切换工作重心，而不是同时铺太多线。

## 13. 微信小游戏版的技术控制重点

需要特别控制的不是“技术先进性”，而是：
- 包体大小
- 界面清晰度
- 数值可调试性
- 开发迭代速度

因此项目早期不建议：
- 上复杂 ECS 架构
- 引入大量第三方框架
- 提前设计 PC 与小游戏共用的超大底层

先做出一个能反复改、能迅速验证的版本更重要。

## 14. 当前推荐结论

当前最适合你的组合是：

- 引擎：`Cocos Creator`
- 语言：`TypeScript`
- 文档：`Markdown`
- 数值：`Excel`
- 原型：`Figma`
- 存档：本地优先
- 后端：后续按需接微信云开发
- 素材策略：采购通用件 + 自制核心件 + AI 辅助概念图

这套组合对微信小游戏来说足够务实，也最适合你现在“先把正确版本做出来”的阶段。
