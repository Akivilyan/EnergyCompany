# 可玩性与数值验证

本文合并旧的 v0 检查点、目标线、调参面板和灾害政策，只保留仍会被执行的验证方法。当前模块以看板为准。

## 目标

验证玩家是否能理解并主动完成经营循环，而不只是验证模拟可运行。数值调整服务于决策节奏；未经试玩证据，不扩大系统和内容。

## 记录项

每次试玩只记录以下内容：

- 设备、分辨率、版本 commit
- 完成路线与用时
- 首个看不懂或点不到的位置
- 玩家对“当前目标、刚发生的变化、下一步”的复述
- 首次有意义的建设/研发取舍
- 卡住、破产、退出或完成位置
- 建议只归入：界面表达、反馈、节奏、数值四类

## 核心检查点

| 检查点 | 观察内容 |
|--------|----------|
| 开局 1 分钟 | 能否识别资金、供能、SV、建设和下一月 |
| 第一次建设 | 候选差异、成本、工期、预期收益是否明确 |
| 第一次推月 | 能否解释资金与供能变化 |
| 第一次压力反馈 | 是否知道问题来源和可采取的动作 |
| 第一个阶段目标 | 是否知道解锁条件和大致进度 |
| 结束/退出 | 是否愿意继续以及原因 |

## 调参边界

优先调整配置中的起始资金、设施造价/工期/产能、需求、收入、SV 门槛和灾害惩罚。每轮最多调整 3–4 个同一目的参数，并保留前后试玩记录。

以下属于玩法规则，不因单次试玩直接修改：月度结算顺序、双主资源、公司等级只升不降、连续两月负资金失败、固定灾害轴和技术效果语义。确需修改时先回到对应 GDD 解决设计冲突。

## 自动化的角色

- `npm test`：保护规则不变量和高价值用户路径。
- 代理路线：用于发现必死局、无解门槛和极端数值，不代替真人试玩。
- 截图/预览探测：用于发现重叠、截断、缩放和层级问题，不评价乐趣。
- 静态 token 检查：只保护架构约定，不作为玩家体验通过条件。
