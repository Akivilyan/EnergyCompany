# 开发策略：从工程闭环回到可玩闭环

本文定义长期开发方向和阶段门，不记录当前模块状态；当前态只看 `PROJECT-TASK-BOARD.md`。

## 结论

项目不应为了“保住已有成果”继续维护错误路径。当前规则层边界清楚、测试稳定，暂时值得保留；外围壳层、重复适配和验证工具则必须按是否帮助玩家体验重新审判。接下来采用 **可玩切片优先 + 允许推倒重建**：先把一条短流程做到真实可读、可操作、可复测，再扩内容、地图、美术和商业化。

## 审计依据（2026-07-12）

- `src/sim/` 约 2,100 行，规则与序列化有稳定单测；全仓 411 个测试通过。
- `src/app/` 与 Cocos 客户端脚本合计超过 14,000 行，外围装配和展示层远大于规则核心。
- `src/app/` 存在 30 余个专项 CLI；不少脚本是在重复证明相邻的装配或路线。
- `docs/design/` 原有 82 份文档、约 9,700 行，仍大量引用已结束的 T 编号和实现前草案。
- `verify:client:fast` 主要验证源码标记、节点、slot/token 和程序化路线；这些护栏全部通过，但现有手机预览截图仍出现小字、遮挡、层级竞争和调试壳观感。
- 看板曾把闭环、商业化、发布、UI 壳全部标记为 `done`，但没有给出一个可由真实玩家验收的版本定义。

## 推进困难的根因

### 1. 完成定义与产品价值脱节

“存在、可调用、自动化通过”被当成“玩家可用”。结果是结构越来越完整，但界面和节奏没有形成可交付体验。

### 2. 范围提前膨胀

在首局体验尚未稳定前，项目已经实现或暴露大地图、超级水电、商业化、长战役、多页面壳等后期能力。每增加一个系统，就同时扩张规则、模块、HUD、Cocos、文档和验证面。

### 3. 同一事实有过多表达层

GDD、Feature、UI、工程草案、代码、CLI 和测试重复描述接口与状态。旧任务号和“未来实现建议”在实现完成后仍保留，阅读成本高，也容易误导新会话。

### 4. 验证倒金字塔

规则测试是有效资产；大量静态 token、源码字符串和专项 CLI 的边际价值已经很低。它们能阻止文件被删，却不能发现字号太小、卡片重叠、主操作不清楚。

### 5. 缺少短周期真人反馈

代理路线和自动化回归证明数值能走通，不等于经营决策有趣。原设计需要较长时间触达关键节点，导致每次 UI 或节奏判断的反馈周期过长。

## 保留、推翻与延后

### 保留，但不神化

- `src/sim/` 的命令、月结、序列化与规则测试：目前边界正确、回归稳定；只有当玩法设计本身变化或接口阻碍切片时才重构。
- `src/modules/` 的状态写入边界：继续保证 UI 不直接改 `GameState`，具体类和文件可合并或删除。
- 存档 schema、配置 ID 和平台端口：涉及兼容性，变更时必须有迁移或明确舍弃策略。

### 优先推翻候选

- `CityHudPanel` 虽已拆出 screen panel，仍约 1,600 行并掌握大量布局、slot 和状态同步；若首局页面继续受它限制，应改成更小的根宿主，城市页也进入独立 screen，而不是继续在单体上打补丁。
- `cityHudStageSpec`、`uiShellStageSpec` 及其大量 token：只保留真正的资源/层级契约；为 placeholder 或历史验收存在的 manifest 可删除。
- `cocosHudCloseCheck` 与 `verify:client:fast` 中逐字符串、逐 token 的静态清单：它们把实现形状误当成行为契约。改为少量架构边界、类型检查和真实路线 smoke 后，删除同义检查。
- `src/app/` 中为历史阶段创建的专项 CLI：先画出仍被 package script、测试或人工流程使用的入口，未使用且与现有测试重复的直接删除。
- controller → display builder → Cocos view model 的重复映射：以当前切片为单位合并，只保留一次业务快照到视图模型的转换。

### 延后，不再占用主线

- World、Region、Tech、商业化、超级水电和长战役的既有实现可以暂时留在仓库，但不得迫使首局 UI 兼容其布局或验收项。
- 延后模块若持续增加当前维护成本，可以删除 UI/适配实现，保留规则与设计，未来按稳定模式重建。

## 推翻判据

满足任一项即可进入删除/替换评估，不需要因为“已经做完”而保留：

1. 修改一个玩家动作需要跨三个以上展示映射层同步同一字段。
2. 测试主要断言文件名、源码字符串、token 或节点存在，而不验证玩家行为。
3. 组件为了兼容未进入当前切片的页面而牺牲可读性、布局或交互。
4. 工具只复现已有单测/路线，且没有独立故障发现能力。
5. 文档描述已完成的实现步骤，而不是当前规则、边界或未来决策。

推翻时先写出要保护的行为与数据，再删除旧结构并用最短路径重建；不做“旧新两套长期并存”的迁移。

## 新的阶段门

### 阶段 A：首局可玩切片

用现有规则和教学配置完成 10–15 分钟开发验收路线：开局 → 建造 → 推月 → 看懂资金/供能/SV 变化 → 处理一次压力反馈 → 明确下一目标。开发验收路线可加速，但不得另造一套结算规则。

通过条件：两种目标手机尺寸无重叠/截断；正文不低于约 16sp 的可读效果、关键信息有更强层级；触控热区至少达到约 48×48dp 且相邻操作不误触；文字在场景背景上有稳定对比；玩家不看文档也能说出当前目标、刚才发生了什么、下一步能做什么。

### 阶段 B：核心经营决策

只验证三件事：建设选择有取舍、推月结果可解释、短中期目标能驱动下一步。根据真人试玩调整信息呈现和少量数据，不扩新系统。

通过条件：至少 3 次独立试玩；记录首个困惑点、首次有效决策、卡住位置和退出原因；关键问题收敛后再进入下一阶段。

### 阶段 C：页面纵向补齐

按真实流程逐页补齐 Company、Tech、Region、World，而不是同时铺开。每次只接入当前路线需要的页面与动作；页面必须先过可读性与交互验收，再补装饰资源。

### 阶段 D：内容、美术与引导

核心页面稳定后再批量生产正式资产、扩地图内容和完善引导。引导解释稳定交互，不用于掩盖不清晰的界面。

### 阶段 E：商业化与发布

真实广告位、IAP、真机渠道差异放在留存与流程成立之后。stub 通过只能证明回退链路，不能标记真实商业化完成。

## 范围冻结

在阶段 A、B 通过前，默认冻结：新玩法系统、超级水电扩展、全图内容扩充、随机事件池、IAP、批量美术资产和新的专项验证 CLI。发现问题优先删除、合并或重建，不新增兼容层；旧结构与首局目标冲突时，以首局目标为准。

## 文档真理层

| 事实 | 唯一入口 |
|------|----------|
| 产品目标与玩法规则 | `gdd/` |
| 单功能输入、输出、边界 | `features/` 对应文档 |
| 屏幕关系与美术方向 | `ui/00-screen-map.md`、`ui/art-direction.md` |
| 配置字段与当前数据 | `data/` 与 JSON |
| 代码依赖边界 | `engineering/architecture.md` |
| 长期交付策略 | 本文 |
| 当前模块与下一步 | `engineering/PROJECT-TASK-BOARD.md` |
| 已完成实现与历史 | Git、代码和测试 |

实现完成后不保留独立 API 草案、旧任务拆条或阶段流水。代码签名由 TypeScript 源码表达，行为回归由测试表达。

## 验证策略

验证分三层，顺序不可颠倒：

1. 产品证据：目标尺寸截图/录像、完整点击路线、简短试玩记录。
2. 行为证据：核心用户路径和规则不变量测试。
3. 结构护栏：类型检查、边界检查、少量架构约束。

结构护栏失败必须修复，但结构护栏通过不代表模块完成。
