# 技术选型定稿（微信小游戏 + 配置驱动模拟层）

## 1. 结论（先给答案）

在当前项目边界下（微信小游戏首发、Playable v0 快速验证、配置驱动模拟为核心），**主栈定为：Cocos Creator + TypeScript + 纯 TS 模拟核心**，不以 Unity 作为 v0 主引擎。

> 定位：先把「可测、可迭代、可上线」放在第一优先级，而非追求跨平台 3D 能力上限。

---

## 2. 选型前提（T41 对齐）

本次选型以以下约束为准：

- **平台优先级**：微信小游戏优先，需兼顾包体、启动时延、低端机稳定性。
- **玩法形态**：2D 界面 + 月度结算 + 配置驱动规则，非重 3D、非实时动作。
- **研发目标**：先完成 v0 内测闭环，再逐步扩展系统深度。
- **工程目标**：模拟层可脱离引擎独立测试，规则迭代不依赖 UI 层改动。

---

## 3. 引擎审稿：Unity 在中国是否仍优选

结论分两层：

1. **行业层面**：Unity 在中国仍有成熟人才池、资产生态和商业项目经验，不能简单判定为“不行”。  
2. **本项目层面**：针对「微信小游戏 + 配置驱动模拟」的 v0 目标，Unity **不是当前优选**。

### 3.1 Unity 的优势（客观成立）

- 招聘与外包生态成熟，工程化工具链完善。
- 编辑器工作流与资产商店生态完整，适合中大型内容生产。
- 若后续升级为中重度 3D / 多平台同步发行，迁移成本可能更低。

### 3.2 Unity 在本项目的主要风险

- 微信小游戏链路上，Unity 适配通常需要额外桥接与平台特化处理，**维护复杂度偏高**。
- 对于当前以 UI 与数值结算为主的玩法，Unity 的能力上限短期难以转化为收益。
- v0 阶段更需要快速迭代配置与规则验证，Unity 在此类「轻表现、重模拟」项目上并非效率最优。

### 3.3 何时才建议改回 Unity

仅当后续出现以下条件，再考虑切换：

- 明确转向中重度 3D 表现（复杂场景、镜头、物理与大量特效）。
- 明确要求多端高一致发行（小游戏只是其中一个渠道）。
- 团队已形成稳定 Unity 产线，且能接受平台适配成本。

## 4. 主栈定稿（T42）

| 层 | 定稿 |
|----|------|
| 客户端引擎层 | **Cocos Creator 3.x（2D）** |
| 主要语言 | **TypeScript** |
| 模拟核心层 | **纯 TS（无引擎依赖）** |
| 配置数据 | JSON（由 Excel/表工具导出） |
| 存档 | 小游戏本地存储（JSON + 版本号） |
| 测试 | 模拟层单测 + 关键结算快照测试 |

说明：

- 引擎仅负责渲染、输入、UI 编排、平台生命周期对接。
- 核心规则（资金、供能、SV、事件、科技、结算管道）全部放入模拟层。
- 保持「同一套规则可在 Node 测试环境跑通」。

---

## 5. 目录结构（建议）

```text
src/
  app/                     # 启动、路由、场景切换、平台生命周期
  ui/                      # 页面与组件（world/region/city/company/tech/events）
  modules/                 # 业务编排（建造、研发、借贷、广告入口等）
  sim/                     # 纯 TS 模拟核心（不可引用引擎 API）
    core/                  # GameState、结算主循环、命令执行
    systems/               # supply / social_value / tech / events / economy
    adapters/              # 读配置、写存档、随机数/时间注入
    types/                 # 领域类型与枚举
  config/
    generated/             # 表工具导出的 JSON（只读）
    schema/                # 配置结构约定与校验规则
  infra/
    storage/               # 本地存档封装（版本迁移）
    analytics/             # 埋点接口（可 stub）
    monetization/          # 广告/IAP 接口（v0 可 stub）
tests/
  sim/                     # 模拟层单测与结算快照测试
tools/
  config-pipeline/         # 导表、校验、差异检查脚本
```

边界规则：

- `sim/` 不允许引用 `cc` 或任意 UI 层对象。
- `ui/` 不直接改写存档，仅通过 `modules/` 发命令到 `sim/`。
- `config/generated/` 视为外部输入，不在运行时动态改结构。

---

## 6. 配置加载方式（配置驱动模拟层）

## 6.1 数据流

`Excel/策划表 -> 导表脚本 -> JSON -> schema 校验 -> 打包进 config/generated -> 启动时加载 -> 注入 sim`

## 6.2 运行时策略

- 首次启动一次性加载核心表（区域、设施、科技、公司等级、事件战役轴）。
- 建立只读 `ConfigRepo`，按 `id` 索引查询。
- `run_config`（方针、难度、战役）作为参数注入模拟层，不在 UI 写死分支。

## 6.3 数值与确定性约束

- 结算全程整数，禁止在核心流程中使用浮点累计误差。
- 随机事件入口预留 `RngPort`，可注入固定种子以复现实验局。
- 月度结算输出可序列化，支持快照回归测试。

---

## 7. 关键技术决策（ADR 摘要）

- **ADR-01**：平台优先级 = 微信小游戏优先，因此引擎需优先满足小游戏链路效率。
- **ADR-02**：玩法是「重规则、轻表现」，模拟层必须独立于引擎。
- **ADR-03**：配置是规则输入而非代码常量，导表与校验为必选项。
- **ADR-04**：商业化与平台 SDK 在 v0 允许 stub，但接口必须先抽象。

---

## 8. 里程碑落地建议（衔接 T43/T44）

1. 在 T43 固化模块依赖图：`ui -> modules -> sim -> infra` 单向依赖。  
2. 在 T44 定义模拟层核心接口：`dispatch(command)`, `settleNextMonth(state, config)`, `serialize(state)`。  
3. 先实现最小可测闭环：单城建造 + 推月 + 供能/SV 结算 + 存档。  
4. 再接区域电网、科技、灾害轴与公司经营。  

---

## 9. 风险与缓解

| 风险 | 触发信号 | 缓解 |
|------|----------|------|
| 引擎逻辑侵入模拟层 | `sim/` 出现引擎依赖 | 加 lint 规则与目录边界检查 |
| 配置变更导致回归 | 同一局结果不稳定 | 增加结算快照测试与导表 diff |
| 平台 SDK 阻塞主线 | 广告/IAP 调试反复卡住 | v0 先 stub，功能完成后再联调 |
| 过早优化画面 | 核心循环验证被拖慢 | 阶段内冻结美术深度，先验玩法 |
